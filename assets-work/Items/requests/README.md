# Item regeneration requests

An item request asks the art builder (a Codex agent following [`ASTRA.md`](../../../ASTRA.md)) to
improve, repaint or redesign an item that is already in the game: a weapon, shield, armour part,
wing, jewel, pet or any other item with a model. The owner files it from the in-client item editor
(**Ask Codex...**) or by hand. It is the item counterpart of the World1 contract
([`../../World1/requests/README.md`](../../World1/requests/README.md)): same lifecycle, same frozen
fields, same worker rules. What differs is written down here.

A request only **replaces an existing item's look in place**: same group and index, same file
names. New items, and changes to names, stats, size or class requirements, are never art
requests (they need the item table, `OpenItems()` and OpenMU; see
[`ITEM_EDITOR_PLAN.md`](../../../docs/agents/ITEM_EDITOR_PLAN.md) section 8).

## Files

```
assets-work/Items/requests/
  README.md              this contract
  request.schema.json    JSON Schema (draft 2020-12) for request.json, schema "mu-item-regen-request/1"
  validate_request.py    stdlib-only validator (shape, catalog, scope, must_keep and git checks)
  codex-prompt.md        the owner's prompt that starts a Codex worker on one request (the editor's
                         Requests tab copies it with the request's id, branch and worker label)
  <YYYY-MM-DD>-<item-key>-<slug>/
    request.json         the contract; the only file tools read
    brief.md             the same request written for people and agents (generated by the editor)
    captures/*.jpg       in-client screenshots, JPEG, at most 1920 px wide (the repo has no LFS)
    captures/ref-*.jpg   the owner's reference images (optional), same limits
    owner-decision.json  the owner's Accept / Reject with notes from the editor (optional, see Lifecycle)
    delivery/<item-key>/ written by the worker; see "Worker rules"
```

- `<item-key>` is the first target's catalog key `<group>-<index>` (`0-0` is the Kris,
  `7-1` the Dragon Helm). `<slug>` is one to five lower-case words joined by `-`. The folder name
  is the request `id`: `2026-09-23-0-0-sharper-blade`.
- The worker's branch is `codex/item-req-<item-key>-<slug>` and its worktree the sibling folder
  `../MuMain-item-req-<item-key>-<slug>`. The validator rejects a `<item-key>-<slug>` that another
  request folder already uses, so branch names are never reused.
- There is no `world` field. `author` is `"owner (item editor)"` and the first `status_history`
  entry is `by: "item editor"` when the editor files the request.
- Every path is relative to the repository root, uses `/` and never contains `..`, except
  `handoff.worktree`.

## Where the facts come from: `catalog.json`

[`../catalog.json`](../catalog.json) ("mu-item-catalog/1", see [`../README.md`](../README.md)) is
the per-item file the editor reads, keyed `<group>-<index>`. A request copies each target's facts
from it: `key`, `group`, `index`, `name`, `family`, `tier` (the catalog's `tier.value`), `classes`
(`table.classes`), `size` (`[table.width, table.height]`), `armour_set` (`armour_set.index` or
`null`), `original` and `models`. Each model keeps `role`, `class` (class variants only), `bmd` and
`textures` from the catalog and adds `current_sha256`, the SHA-256 of the BMD at `base_commit`.
While a request is `open`, `claimed` or `delivered`, the validator requires these to equal the
catalog.

An item can have several models: its own (`role` `item`, always first), per-class replacements
the engine draws instead (`class-variant`: Summoner, Rage Fighter and Dark Lord armour/helm
variants), the left and right hand models of Rage Fighter gloves (`left-hand`, `right-hand`) and
models the inventory draws instead (`inventory`). They all belong to the request.

## Kinds

| Kind | Meaning | Owned files | Must keep (the kind's `must_keep` line) |
|------|---------|-------------|------------------------------------------|
| `upscale` | same design, better textures (resolution, detail, cleaner UVs) | non-frozen target textures | mesh, UVs unless noted, suffixes |
| `repaint` | new colours/materials on the same mesh | non-frozen target textures | mesh, UV layout |
| `remodel` | better geometry, same silhouette and function | target BMDs and non-frozen target textures | origin, orientation, scale, mesh order |
| `redesign` | new look for the same item (the owner describes it, may attach reference images) | target BMDs and non-frozen target textures | origin, grip, size in slot, mesh order |
| `set` | `change.set_kind` (one of the above) for two or more parts of one armour set | as for `set_kind` | per-part skeleton and actions, the parts read as one set |

A `set` request's targets are armour parts (groups 7-11) with the same `armour_set` index; the
editor offers all parts of the clicked part's set. Every other kind has no `change.set_kind`.

## What a rebuilt item keeps: `constraints.must_keep`

`must_keep` contains these lines verbatim (the validator checks them), then the line of the kind
(for `set`: the line of `set_kind` and the set line). Owner-specific wishes go into `change.keep`.

Common:

- `File names and paths: no renamed, added or deleted game files`
- `Origin, orientation and scale: hands, back and shields attach through the model origin (RenderLinkObject angles are hard-coded)`
- `Mesh count and mesh/material order (the engine hides and blends meshes by index)`
- `Texture name suffixes _R, _S, _H, _N (they set render flags); no new ones`
- `At most 1500 triangles per model; power-of-two textures up to 1024 px, .jpg opaque, 32-bit .tga for alpha`
- `Armour and wings: the skeleton (bone count, order, names, parents) and every action with its key count`
- `Size in the inventory (Width x Height of the item table) and a footprint that fits it`

Per kind:

- upscale: `Upscale: the design, the mesh and the UV layout (unless the request says otherwise), the texture name suffixes`
- repaint: `Repaint: the mesh and the UV layout`
- remodel: `Remodel: the silhouette and the function; origin, orientation, scale and mesh order`
- redesign: `Redesign: origin, grip, size in the inventory slot and mesh order`
- set: `Set: every part keeps its skeleton and actions, and the parts still read as one set`

`constraints.limits` is always `{"max_triangles": 1500, "max_texture_size": 1024}`.

The engine effects (+7..+15 glow, excellent shine, ancient effect) are drawn by code in
`RenderPartObjectEffect`, not by the asset; a request cannot change them. They are shown in the
`glow` captures so the worker sees how the new texture will look under them.

## How the game draws the item: `constraints.render` and the render lines

The client draws some meshes blended, and that decides how their texture has to be painted: an
opaque repaint of an additive wing turns into hard streaks or white blades in the game (the
Wing01 pilot). [`../render-facts.json`](../render-facts.json) records, per item, model and mesh,
how the engine draws it when **worn**, **dropped** (on the ground) and in the **inventory**, and
what it adds on top; [`../README.md`](../README.md) ("How the game draws items") explains the modes
and effects. A request copies both:

- `constraints.render`: an object keyed by target key; each value is
  `{"models": [...], "effects": [...]}`. `models` is the target's `render-facts.json` `models`
  with, per model, `role`, `bmd` and `meshes`, and per mesh only `mesh`, `texture`, `worn`,
  `dropped` and `inventory` (a mode, or `null` where the model is not used). `effects` is the
  target's `request.effects`: the +level and excellent sentences, then every effect the engine
  adds (sprites, particles, joints, extra mesh passes, UV animation, pulsing, cloth).
- After the kind's lines, `constraints.must_keep` gets every target's `request.must_keep` lines
  verbatim (each line once), one per model and mode that occurs:
  - `Blended meshes of <bmd> (mesh 0 | meshes 0, 1): the game draws them additively - paint on black (black is fully transparent, brightness becomes glow); no opaque background, no baked dark outlines`
  - `Alpha-blended meshes of <bmd> (...): the game draws them see-through at partial opacity - keep them light and even; no opaque background, nothing that has to read as solid`
  - `Cut-out meshes of <bmd> (...): the game discards texels at or below 25% alpha and blends the rest - keep the 32-bit .tga alpha as the silhouette; no opaque background, no matte fringe`

  `<bmd>` is the file name of the model (`Wing01.bmd`). A mesh counts when any of worn, dropped or
  inventory draws it that way. Opaque meshes get no line. For the Wings of Elf (`12-0`) the line is
  `Blended meshes of Wing01.bmd (mesh 0): the game draws them additively - paint on black (black is fully transparent, brightness becomes glow); no opaque background, no baked dark outlines`.

While the request is live the validator requires `constraints.render` and these lines to equal
`render-facts.json`; rebuild it with `python3 tools/item_editor/render_facts.py` when the engine's
item render code or a model changes.

## How the editor fills a request

- `base_commit`: the full sha of the checkout's `HEAD` (it must be on `origin`).
- `targets[]`: from the catalog, the clicked item first (see above).
- `constraints.shared_textures`: every target texture container that another consumer also uses,
  mapped to all consumers, the targets included: item keys sorted by group and index, then
  non-item models as `other:<MODEL_...>` sorted by name (the order of `shared_with` in the
  catalog).
- `constraints.frozen_textures`: every shared container with a consumer outside the targets, every
  container outside `src/bin/Data/Item/` and `src/bin/Data/Player/`, and anything the owner
  freezes. To change a shared texture, add its other items as targets.
- `constraints.owned_files`: the files the worker may replace (table above), never a frozen one.
- `constraints.protected_paths`: at least `src/source/`, `src/MuEditor/` and
  `assets-work/Items/catalog.json`; the editor writes the list of the example.
- `constraints.must_keep` and `constraints.limits`: as above; `constraints.render` and the render
  lines from `render-facts.json` (the editor reads it next to `catalog.json`).
- `change`: the owner's summary, details, keep and avoid; `set_kind` for a set;
  `reference_images` for the images the owner attached, copied to `captures/ref-1.jpg`, ...
- `evidence.captures`: one entry per screenshot without the editor overlay: `view` is `inventory`,
  `ground`, `equipped-front`, `equipped-side`, `turntable` (with `angle`), `glow` (with
  `item_level` and `excellent`) or `other`; `variant` is `current` (or `original`/`candidate` in
  A/B); `resolution` is the JPEG's `[width, height]`; `client_commit` the short sha the client was
  built from, or `null`.
- `handoff`: derived from the id; `push_allowed` stays `false` unless the owner ticks it.

## Lifecycle

```
open ──> claimed ──> delivered ──> accepted
  │         │            └───────> rejected
  └─────────┴──> withdrawn
```

Unchanged from World1, with the item paths:

| Step | Who | Where | Changes |
|------|-----|-------|---------|
| open | owner / item editor | filing commit on `main` (`docs(assets): file item request <id>`), pushed to `origin` | The folder with every field set: `status` `open`, one `status_history` entry, `null` for the claim, `result` and `decision`. |
| assign | coordinator | `main`, pushed | An entry in `assets-work/Items/assignments.json`: `"<worker label>": {"request": "<id>", "branch": ..., "worktree": ...}`. No field in `request.json` changes. |
| claimed | the assigned Codex worker | its own branch and worktree | `status` `claimed`, `handoff.claimed_by` (the worker label), `claimed_at`, `start_commit`, one `status_history` entry. |
| delivered | the same worker | same branch | Writes `delivery/`, installs owned files, sets `result`, `status` `delivered`, one `status_history` entry. |
| owner verdict | owner (item editor: **Accept** / **Reject with notes**) | the worker branch, pulled locally | Writes `owner-decision.json` `{"verdict": "accept" or "reject", "notes": "...", "date": "YYYY-MM-DD"}`. Nothing else. |
| accepted | coordinator only | integration on `main` | Merges the worker branch, sets `decision` (`status`, `at`, `by`, `reason`, `ledger_entry` `requests/<id>/delivery`), `status`, one `status_history` entry; regenerates the catalog. |
| rejected | coordinator only | `main` | Sets `decision`, `status`, one `status_history` entry. The worker branch is not merged. A rejection with notes can be re-filed as a new request whose `supersedes` names this one. |
| withdrawn | owner only | `main`, before a decision | `decision` `withdrawn`, `status`, one `status_history` entry. |

Frozen once `open`: `schema`, `id`, `created`, `author`, `priority`, `kind`, `base_commit`,
`supersedes`, `targets`, `change`, `constraints`, `evidence`, `brief.md`, `captures/`, and in
`handoff` the fields `repo`, `branch`, `worktree`, `deliver_to` and `push_allowed`.
`status_history` is append-only. If the request itself is wrong, the owner withdraws it and files
a new one.

## Worker rules (Codex)

1. Take only a request assigned to you in `assets-work/Items/assignments.json`. Create the
   worktree from the `main` commit that contains the filed request and the assignment:
   `git fetch origin && git worktree add ../MuMain-item-req-<item-key>-<slug> -b codex/item-req-<item-key>-<slug> origin/main`.
   Set `handoff.start_commit` (`git rev-parse HEAD`, 40 characters), `claimed_by`, `claimed_at`,
   `status` `claimed`, append to `status_history`, run the validator and commit the claim
   (`docs(assets): claim item request <id>`) before you produce anything. If the validator says
   the request is stale, stop and tell the owner.
2. Read `brief.md`, `request.json`, the targets' catalog entries (models, textures, `shared_with`,
   structure), their `render-facts.json` entries (which meshes the game blends, what it adds on
   top) and [`ASTRA.md`](../../../ASTRA.md) (weapons, armour, "How the game draws items"). Paint a
   blended mesh for blending and never paint the engine's effects into a texture.
3. `constraints` are binding and the validator checks your working tree against `start_commit`:
   change only `owned_files` (replace, never add, delete or rename), never a frozen texture or a
   protected path; outside the request folder change nothing else but `docs/agents/WORKLOG.md`;
   keep every `must_keep` line and the `limits`.
4. Deliver into `assets-work/Items/requests/<id>/delivery/<item-key>/` per target: `original/`
   (the item's own BMD and every owned file of that item, byte-identical to `base_commit`, plus
   their `bmdconv info`), `source.blend`, `exports/`, `review/` (before/after, wireframe, inventory
   size, in hand or on the body), `validation/summary.json` (with the raw output of
   `bmdconv validate`, `bmdconv compare` and `tools/mu_texture.py check`) and `notes.md`.
5. Install only `owned_files` into `src/bin/Data/Item/` or `src/bin/Data/Player/`, byte-identical
   to their exports. Files there are matched by `**/bin/**` in `.gitignore` but tracked, so
   `git add` works.
6. Fill `result` (`delivered_at`, `source_commits`, `installed_files` game path -> export,
   `validation`, `review_images`, `notes`, `pr_url`), set `status` `delivered`, append to
   `status_history`, run the validator and commit. Push and open a PR on `vaskodagamo/MuMain`
   only when `handoff.push_allowed` is `true`; never merge.
7. Never set `accepted` or `rejected`, never write `owner-decision.json`, never edit
   `catalog.json`, `tiers.json`, `assignments.json`, `client-review.json` or another request's
   folder. Record your session in `docs/agents/WORKLOG.md`. Evidence is offline; never claim a
   client check.

## Git rules for this fork

- Only the fork `vaskodagamo/MuMain` (`origin`); always `gh ... --repo vaskodagamo/MuMain`.
- Never push to `upstream` (`sven-n/MuMain`) and never open a PR there.
- Push or open a PR only with the owner's explicit authorization (`handoff.push_allowed`). Never merge.
- Fetch and fast-forward `main` before building for a client check; merges happen on GitHub.

## Validate

```bash
python3 assets-work/Items/requests/validate_request.py assets-work/Items/requests/<id>
python3 assets-work/Items/requests/validate_request.py --all
```

Besides the schema, the validator checks that the id, folder, branch, worktree and `deliver_to`
agree; every path exists; targets are catalog items and, while live, equal the catalog and
`render-facts.json` (`constraints.render` and the render lines of `must_keep`); a set
covers one armour set; shared and frozen textures are complete; owned files fit the kind and are
never frozen or protected; `must_keep` has the lines of the kind; captures and reference images
are JPEGs at most 1920 px wide whose size equals `resolution`; `base_commit` holds every target
model's `current_sha256`; a claimed or delivered request has an assignment and a `start_commit`
that contains the filed request with the same target files; the worker branch changes nothing
outside its scope; delivered originals equal `base_commit` and installed files equal their
exports; `owner-decision.json`, when present, has a valid verdict.
