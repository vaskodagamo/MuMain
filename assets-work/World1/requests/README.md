# World1 regeneration requests

A regeneration request asks the art builder (a Codex agent following [`ASTRA.md`](../../../ASTRA.md))
to rework one Lorencia (World1) model that is already in the game. The owner files it from the
in-client world editor (**Flag for regeneration**) or by hand; it replaces feedback given in chat.
The request is one folder with a machine contract (`request.json`), a readable brief and
screenshots. Each request has its own folder and there is no shared index file, so parallel
requests never cause merge conflicts.

Placement, rotation, scale, terrain height, texture layers, lightmap and walkability are **never**
art requests. The owner changes them in the editor on their own branch.

## Files

```
assets-work/World1/requests/
  README.md              this contract
  request.schema.json    JSON Schema (draft 2020-12) for request.json, schema "mu-regen-request/1"
  validate_request.py    stdlib-only validator (shape, catalog, git and scope checks)
  <YYYY-MM-DD>-<model>-<slug>/
    request.json         the contract; the only file tools read
    brief.md             the same request written for people and agents (generated by the editor)
    captures/*.jpg       in-client screenshots, JPEG, at most 1920 px wide (the repo has no LFS)
    delivery/<Model>/    written by the worker; see "Worker rules" (a new variant uses <NewModel>)
```

- The owner writes `request.json`, `brief.md` and `captures/`. After filing, the worker changes
  only the claim and result fields of `request.json` and writes `delivery/`.
- `<model>` is the first target's model name in lower case (`sign01`). `<slug>` is one to five
  lower-case words joined by `-` (`readable-board`). The folder name is the request `id`.
- The worker's branch is `codex/lorencia-req-<model>-<slug>` and its worktree is the sibling folder
  `../MuMain-lorencia-req-<model>-<slug>`. The validator rejects a `<model>-<slug>` that another
  request folder already uses, so branch names are never reused.
- Every path inside `request.json` is relative to the repository root, uses `/`, and never
  contains `..`. The one exception is `handoff.worktree`, which points at a sibling folder
  outside the repository (`../MuMain-lorencia-req-...`).

## Where the facts come from: `catalog.json`

[`../catalog.json`](../catalog.json) is the single per-model file the editor reads. It is generated
by [`../coordination/build_editor_catalog.py`](../coordination/build_editor_catalog.py) from the
coordination files and the git history of `HEAD`. Never edit it by hand; re-run the script on
`main` instead (`--check` exits 1 when it is out of date).

- `models` is an object keyed by the decimal World1 object type (`"96"`), which equals
  `OBJECT::Type` of a placed Lorencia object. In C++: `catalog.at("models").find(std::to_string(type))`.
  nlohmann's default `json` iterates keys as strings (`"0"`, `"1"`, `"10"`, ...). Sort by the
  entry's `type` for display.
- `untyped_models` is keyed by model name. It holds the fauna BMDs (Bird01, Butterfly01, Fish01)
  that code spawns and that never appear in `EncTerrain1.obj`.
- Each entry has:
  - `name`, `type`, `bmd`, `in_scope`, `exclusion`, and `identity`, the text the
    [asset board](../coordination/asset-board.md) shows.
  - `status`, as on the asset board: `accepted` (integrated, including the four pilot props, whose
    first batch is named `pilot`), `blocked` (excluded from the art scope, kept byte-identical),
    `in-progress` (reserved in `production-batches.json` but never integrated) or `unchanged` (in
    scope but never produced).
  - `client_verified` and `client_review`: the owner's own verdict from the client (see
    "Client verdicts" below). `client_verified` is `true` only for the verdict `looks-good`;
    `client_review` is `{"verdict", "note", "date"}` or `null` when the owner has not judged the
    model yet.
  - `placement_count`, `first_placement`, `textures` (name in the BMD -> container) and
    `shared_with` (texture name -> the other models that use the same container).
  - `structure`: mesh, bone, action and triangle counts, and `mesh_textures` in mesh order.
  - `engine_controls`: rows from [`engine-controls.md`](../coordination/engine-controls.md), with
    `blend_mesh` and `blend_mesh_texture` resolved.
  - `current_sha256` (working tree), `accepted_sha256` (from the final inspection) and `bmd_modified`.
  - `original` (`revision`, `archive`, `sha256` and `reachable` for the pre-rebuild BMD).
  - `last_batch` and `model_dir`: where the newest `source.blend` is.
  - `batches`, oldest first. Each has `name`, `role` (`primary` or `compatibility`), `owner`,
    `agent`, `branch`, `worktree`, `source_commits`, `integration_commits`, `unreachable_commits`,
    `notes`, `model_dir`, `installed` game files and `original`.
  - `previews` (`baseline` and `final` offline renders, only when the files exist).
  - `requests`: open requests as `id`, `status` and `assigned_to`.
- `batches` lists integrated work only. Its `branch` and `worktree` record where the work was
  produced; they are historical and most of them have been deleted. A worktree is a sibling folder
  name, or `null` when it was not a sibling folder. Live assignments appear as `assigned_to` on
  requests.
- `unreachable_commits` lists recorded commits that `HEAD`'s history does not contain. Most batch
  `source_commits` are like this, because the batch branches were deleted after integration.
  `git show` fails for them in a fresh clone. Use `integration_commits` (all on `main`) and the
  `original.archive` file instead. `original.reachable` says whether
  `git show <revision>:<bmd>` works.
- Top-level `requests` lists every request folder: `id`, `kind`, `models`, `path`, `status` and
  `assigned_to` (the worker label of the coordinator's reservation, or `null`).

## Client verdicts: `client-review.json`

[`../client-review.json`](../client-review.json) holds the owner's quick verdicts after looking at a
model in the client. The world editor writes it (Assets tab: **Looks good in client** and **Needs
work**, with an optional note); the owner may also edit it by hand. It belongs to the owner: agents
never edit it, and it does not exist until the first verdict.

```json
{
  "Sign01": { "date": "2026-09-23", "note": "", "verdict": "looks-good" },
  "Tree02": { "date": "2026-09-23", "note": "crown too dark at night", "verdict": "needs-work" }
}
```

- Keys are World1 model names; `verdict` is `looks-good` or `needs-work`; `date` is `YYYY-MM-DD`;
  `note` is free text (may be empty). A new verdict for a model replaces its old one.
- `build_editor_catalog.py` copies each entry into that model's `client_review` and sets
  `client_verified` for `looks-good`. It refuses a file with an unknown model, verdict or field, so a
  typo never reaches the catalog. After a verdict, `--check` reports the catalog as out of date until
  the script is re-run; commit `client-review.json` and the regenerated `catalog.json` together.
- A verdict is not a request. To have a model reworked, file a request as well.
- Judge the files you mean to judge. The client loads a map from its own `Data` folder, which the
  build copies from `src/bin/Data`, so after a `git pull` it still shows the old files until the
  next build. The Assets tab labels such a model `as built`; **Current** (one model or all) loads
  `src/bin/Data` into the running client first.

## Lifecycle

```
open ──> claimed ──> delivered ──> accepted
  │         │            └───────> rejected
  └─────────┴──> withdrawn
```

| Step | Who | Where | Changes |
|------|-----|-------|---------|
| open | owner / world editor | filing commit on `main`, pushed to `origin` | Creates the folder with every field set: `status` `open`, one `status_history` entry, and `null` for `handoff.claimed_by`, `claimed_at`, `start_commit`, `result` and `decision`. |
| assign | coordinator | coordination commit on `main`, pushed | Picks one worker per request and reserves it in `production-batches.json` (see "Coordinator"). No field in `request.json` changes. |
| claimed | assigned Codex worker | its own branch and worktree | `status` `claimed`, `handoff.claimed_by` (the reservation's worker label), `claimed_at`, `start_commit`, one `status_history` entry. |
| delivered | the same worker | same branch | Writes `delivery/`, installs owned files, then sets `result` (all fields), `status` `delivered` and one `status_history` entry. |
| accepted | coordinator only | integration on `main` | Merges the worker branch, then sets `decision` (`status`, `at`, `by`, `reason`, `ledger_entry`), `status` and one `status_history` entry. The ledger, board and catalog change in the same step. |
| rejected | coordinator only | `main` | Sets `decision`, `status` and one `status_history` entry. The worker branch is not merged. |
| withdrawn | owner only | `main`, any time before a decision | Sets `decision` (`status` `withdrawn`, `reason`, `ledger_entry` `null`), `status` and one `status_history` entry. |

Where each state lives:

- **Filing.** `base_commit` is the full sha of the commit the owner's client was built from, normally
  `main`. It must be on `origin`, so that every worker can fetch it. The filing commit adds only the
  request folder (`docs(assets): file request <id>`). The owner puts it on `main` (cherry-pick it
  when the editor ran on another branch) and pushes it before the coordinator assigns the request.
- **Claim and delivery** exist only on the worker branch. Until acceptance, `main` shows the
  request as `open`. The catalog on `main` shows the reservation as `assigned_to`.
- **Decisions** are made on `main`. Only a decision changes `request.json` on `main` after filing, so
  merging an accepted worker branch never conflicts. For a rejected or withdrawn request, `main`
  goes straight from `open` to the decision. The worker branch is never merged.

Everything else is frozen once the request is `open`: `schema`, `id`, `created`, `author`,
`world`, `priority`, `kind`, `base_commit`, `supersedes`, `targets`, `change`, `constraints`,
`evidence`, `brief.md`, `captures/`, and in `handoff` the fields `repo`, `branch`, `worktree`,
`deliver_to` and `push_allowed`. `status_history` is append-only. The validator compares these with
the filed `request.json` at `start_commit`. If the request itself is wrong, the owner withdraws it
and files a new one whose `supersedes` names the old id. A rejected request is never reopened; the
owner files a follow-up the same way.

## How the editor fills a request

The world editor (Map Editor, **Assets** tab; usage in
[`MAP_EDITOR.md`](../../../src/MuEditor/UI/MapEditor/MAP_EDITOR.md#assets-tab)) records the
checkout's `HEAD` as `base_commit` and hashes each target BMD in the checkout for `current_sha256`,
so a request describes committed files: the dialog warns when the BMD of any target differs from
`catalog.json` or when no branch on `origin` points at `HEAD` yet. It offers the models that share the clicked model's
textures as extra targets, and it runs no other tool: validate the folder yourself before filing.

From the catalog entry of each target (the clicked model first):

- `targets[]`: `model`, `type`, `bmd`, `textures`, `placement_count`, `last_batch`, `model_dir`,
  `original` (`revision`, `archive`) copied from the catalog. `current_sha256` is the SHA-256 of the
  BMD at `base_commit`, which equals the catalog value when the catalog is current.
  `picked_instances` holds the placements the owner clicked (`position`, `rotation`, `scale`,
  `tile`, and `obj_index`, the record index in `EncTerrain1.obj`, when known: the editor leaves it
  out when the checkout's `EncTerrain1.obj` differs from the one git's index records, such as after
  an objects save that is not committed yet, because the records at `base_commit` are then
  numbered differently).
- `constraints.shared_textures`: every target container used by more than one model, mapped to
  all its consumers (sorted, including the target).
- `constraints.frozen_textures`: every shared container that has a consumer outside the targets,
  plus anything the owner freezes. To change a shared texture, add every consumer as a target.
- `constraints.owned_files`: the files the worker may replace. For `repaint`: the non-frozen
  target containers. For `remodel`: the target BMDs. For `repaint+remodel`: both. For
  `new-variant`: nothing (see "New variants").
- `constraints.protected_paths`: at least `src/bin/Data/World1/`, engine and build sources,
  `assets-work/World1/coordination/`, `assets-work/World1/catalog.json` and `docs/agents/HANDOFF.md`
  (see the example).
- `constraints.engine_controls`: every catalog `engine_controls` row of every target, unchanged,
  with `model` added.
- `constraints.must_keep`: the fixed list in the example (file names, skeleton, actions, mesh and
  material order, engine mesh slots, bounds, texture format rules).
- `evidence.captures`: one JPEG per capture, at most 1920 px wide, with its `resolution`, the
  camera state and the client commit. `evidence.offline_previews` holds the catalog `previews`.
- `handoff`: derived from the id. `push_allowed` stays `false` unless the owner ticks it.
- `change.new_model`: only for `new-variant`.
- `brief.md`: the same content as prose, linking `ASTRA.md`, this README, the target's `notes`
  from its batches and the captures.

## New variants

A `new-variant` request asks for an additional model derived from one existing target (exactly one
target), for example a broken variant of a fence. A new World1 object type also needs an engine
table change, which the owner makes separately, so a new variant installs nothing:

- `change.new_model` names it `<Family><NN>`: the target's family (`Sign` for `Sign01`) and a
  number that no `src/bin/Data/Object1/*.bmd`, no World1 model and no other request uses. The
  editor picks the next free number; the validator rejects a name that is already taken.
- `owned_files` and `result.installed_files` stay empty; no game file changes.
- The worker delivers into `delivery/<NewModel>/` with the usual layout. `original/` holds the
  target BMD it derives from, and `exports/` holds `<NewModel>.bmd`. It can reference existing
  containers read-only. New texture containers are named `<newmodel>_<name>.OZJ` or `.OZT` (the
  new model name in lower case first). They must not already exist in `src/bin/Data/Object1/` and
  must not end in an `_R`, `_H`, `_S` or `_N` name flag.

## Worker rules (Codex)

1. Take only a request the coordinator assigned to you: `production-batches.json` has an entry
   keyed by your worker label with `"ledger": "requests/<id>/delivery"`. Create the worktree from
   the `main` commit that contains the filed request and that reservation:
   `git fetch origin && git worktree add ../MuMain-lorencia-req-<model>-<slug> -b codex/lorencia-req-<model>-<slug> origin/main`.
   Set `handoff.start_commit` to that commit (`git rev-parse HEAD`, 40 characters), set
   `claimed_by` to your worker label and `claimed_at`, set `status` to `claimed`, append to
   `status_history`, and run the validator. If it reports that the request is stale (a target file
   changed between `base_commit` and `start_commit`), stop and tell the owner. Commit the claim
   (`docs(assets): claim request <id>`) before you produce anything.
2. Read `brief.md`, `request.json`, the target's catalog entry, the `notes` of every batch listed
   there and [`ASTRA.md`](../../../ASTRA.md). Start from the newest `source.blend` in `model_dir`.
3. `constraints` are binding, and the validator checks your working tree against `start_commit`:
   - never change a `frozen_textures` container, and never change any game file that is not in
     `owned_files`;
   - never change anything under `protected_paths`, and outside the request folder change only
     `owned_files` and `docs/agents/WORKLOG.md`;
   - keep every `engine_controls` requirement (for example, the texture at the `blend_mesh`
     index stays at that index);
   - keep every `must_keep` item: file names (no renames, no new or deleted game files), bone
     count/order/names/parents, the action list with key counts and lock flags, mesh count and
     mesh/material order, bounds and pivots within a few percent, power-of-two textures up to
     1024 (`.jpg` opaque, 32-bit `.tga` for alpha, no new `_R/_H/_S/_N` name flags).
4. Placement and terrain are never part of an art request. Never edit `src/bin/Data/World1/`.
   Never merge or rebase `main` into the request branch; the coordinator integrates it.
5. Deliver into `assets-work/World1/requests/<id>/delivery/<Model>/` with the same per-model layout
   as the existing batches: `original/` (the untouched `<Model>.bmd` and every owned container of
   that model, byte-identical to `base_commit`, plus their `bmdconv info`), `source.blend` (with
   `REF_ORIGINAL`), `exports/`, `review/` (before/after, wireframe, gameplay distance),
   `validation/summary.json` (plus the raw compare/check output) and `notes.md`. Retain earlier
   revisions for comparison, for example in `delivery/<Model>/previous/`.
6. Install only `owned_files` into `src/bin/Data/Object1/`, byte-identical to their exports.
   Files there are matched by `**/bin/**` in `.gitignore`; existing files are tracked, so
   `git add` works for them. Never add new game files.
7. Fill `result`: `delivered_at`, `source_commits`, `installed_files` (every owned file you
   changed, game path -> export), `validation`, `review_images`, `notes` and `pr_url`. Set
   `status` to `delivered`, append to `status_history`, run the validator, and commit.
8. Never set `accepted` or `rejected`. Never edit `production-batches.json`,
   `integration-ledger.json`, `asset-board.md`, `catalog.json` or another request's folder.
   Record your session in `docs/agents/WORKLOG.md`.

All evidence is offline unless the owner checks it in the client; never claim client verification.

## Coordinator

The coordinator alone edits the coordination files, and only the coordinator sets `accepted` or `rejected`.

1. Assign: add an entry to `coordination/production-batches.json` keyed by the worker label. It has
   `models` (the targets), `branch` (from `handoff`), `worktree` (the bare folder name
   `MuMain-lorencia-req-<model>-<slug>`, like the existing entries), `owned_textures` (the owned
   containers), `frozen_textures`, and `"ledger": "requests/<id>/delivery"`, which links the
   reservation to the request and to its future ledger entry. Commit it as
   `docs(assets): reserve request <id>` on `main` and push it.
2. Review the delivery independently (a different agent or the owner). Run `validate_request.py`
   **on the worker's branch**, before merging: its scope check compares the working tree with
   `start_commit`. Check the exports with `bmdconv compare` and `tools/mu_texture.py check`.
3. Accept, in one integration on `main` (`docs(assets): accept request <id>`):
   - Merge the worker's branch.
   - Append one entry to `coordination/integration-ledger.json` named `requests/<id>/delivery`.
     With that name the existing tools resolve `assets-work/World1/<name>/<Model>/original/<Model>.bmd`
     and `.../exports/`. Fill `models`, `owner`, `source_commits`, `integration_commits`,
     `game_files` (= `result.installed_files`), `original_revisions` (model -> the first 8
     characters of `base_commit`, like every other entry) and `notes_path`.
   - A game file belongs to the `game_files` of one batch only. For every replaced file, move its
     entry from the older batch's `game_files` into that batch's `superseded_game_files` as
     `{"export": ..., "superseded_by": "requests/<id>/delivery", "reason": ...}`, like
     Groundcover01's `Grass02.bmd`. Otherwise `validate_integration.check_exports` fails on the
     older batch.
   - Set `decision` and `status`, and append to `status_history`.
   - Re-run Blender `inspect_final.py`. It re-renders every model whose BMD or texture hashes
     changed, including the other consumers of a changed texture, and rewrites its
     `final-inspection/<Model>/provenance.json`. Then run `assemble_final.py` for the gallery.
     `catalog.accepted_sha256` comes from that provenance, and the catalog builder warns while it
     is stale.
   - Re-run `update_board.py` and `build_editor_catalog.py`, and commit everything together.
   - `validate_integration.py` still compares against the pre-merge baseline `ac0f6dd8`, so on
     `main` its scope check also reports unrelated later changes. Adapt it before relying on it.
4. Reject: on `main`, set `decision` (with the reason), `status` and `status_history`, and remove
   the reservation. Do not merge the worker's branch. Withdrawn requests lose their reservation
   the same way.

## Git rules for this fork

- Work only on the fork `vaskodagamo/MuMain` (`origin`). Always pass `--repo vaskodagamo/MuMain`
  to `gh`, because `gh` can default to the parent repository.
- Never push to the `upstream` remote (`sven-n/MuMain`) and never open a PR there.
- Push a branch or open a PR only with the owner's explicit authorization: given in the session,
  or recorded by the owner as `handoff.push_allowed: true`. Never merge; the owner merges.
- One concern per commit, in the existing style: `docs(assets): file|claim|reserve|accept request <id>`,
  `art(world1): <what>` or `feat(assets): <what>` for exports, `art: independently review <id>`.
- Fetch and fast-forward `main` before building for a client check, because merges happen on GitHub.

## Validate

```bash
python3 assets-work/World1/requests/validate_request.py assets-work/World1/requests/<id>
python3 assets-work/World1/requests/validate_request.py --all
python3 assets-work/World1/coordination/build_editor_catalog.py --check   # on main only
```

A worker branch changes game files but not `catalog.json`, so `--check` fails there by design.
The validator checks the schema rules by hand (it needs no packages) and also checks that:

- every path exists and is repository-relative; the id (with a slug of one to five words), folder,
  branch, worktree and `deliver_to` agree; timestamps are RFC 3339 with an offset;
- targets match the dependency map, excluded models cannot be requested, and the shared and frozen
  textures are complete;
- `owned_files` respect the frozen textures and the `kind`; a new variant names a free model;
- while the request is `open`, `claimed` or `delivered`, every target field copied from the catalog
  and every engine-controls row (including `requirement`, `blend_mesh` and `blend_mesh_texture`)
  equal `catalog.json`;
- captures are JPEGs at most 1920 px wide whose size equals `resolution`;
- `base_commit` exists in the clone, and each target's `current_sha256` equals its BMD there;
- a claimed, delivered or accepted request has `start_commit`. That commit contains the filed
  request, the target files there equal `base_commit`, and the frozen fields and earlier history
  are unchanged. A claimed or delivered request also needs a reservation for `claimed_by`;
- on the worker branch, the working tree differs from `start_commit` only in the request's
  `request.json` and `delivery/`, the owned files (replaced, never added or deleted, and listed in
  `installed_files` once delivered) and `docs/agents/WORKLOG.md`;
- a delivered request has the full per-model layout, its `original/` files equal `base_commit`,
  and its installed files equal their exports.
